# Security Assessment

## Protection boundaries

- Client boundary: embeddings, LM head, raw prompts/media, final sampling, and decoded media remain client-owned. `ClientBoundary` wipes its tensor store on close.
- Model custody: each worker receives only an encrypted, transformed stage and separate wrapped key. Plaintext monolithic loading is rejected in strict mode.
- Transport: pinned-certificate QUIC, directional HKDF keys, ChaCha20-Poly1305, nonces, replay windows, rotation, and onion-style hop metadata protect transit. The controller relays opaque bytes without payload keys. Protected remote image/video sessions additionally use ephemeral X25519 agreement and directional AEAD tensor envelopes; workers return transformed latents rather than decoded media. Strict media uses compiled equivariant DiT stages whose requests contain no basis or spatial-permutation secrets; inverse transformation and VAE decode occur on the client. Legacy worker-side latent recovery is explicitly development-only `transport_only` obfuscation and is not a zero-trust guarantee. Source-image editing performs VAE encoding on the client, and video reconstruction/MP4 encoding occurs on the client.
- Memory: page-locked shard staging, request cleanup, physical KV-slot wipes, native zero-on-free, and CUDA masking/scrubbing reduce residual data. Logical and hardware cleanup are distinguished.
- Process: the trusted client and every Fortress role worker disable core files, mark the process non-dumpable, and clear ptrace exceptions before reading secrets (`security.process_hardening`, default on; `--lock-memory` on a role worker also locks pages). This does not stop a root user or a hypervisor on the same host. `SecureMemfd` sealed staging exists as a tested library and is not used by the runtime.
- Optional TEE: AMD SEV-SNP, Intel DCAP, and NVIDIA verifier interfaces validate freshness plus workload/artifact/public-key binding. Strict, TEE, non-TEE, and development policies are explicit. A deployment may require one or a configured set of supported trust roots; AMD and Intel are not incorrectly required on the same host. Remote stage workers issue fresh challenges and clients verify nonce+workload+artifact+public-key-bound evidence locally, with AMD/Intel hardware verifier adapters. NVIDIA report verification supports the local verifier and remote NRAS; composite CPU/GPU acceptance fails unless both evidence paths satisfy policy. No silent downgrade is allowed.

## What is not guaranteed

Orthogonal and contragredient transformations are computational obfuscation, not FHE, secret sharing, or a zero-knowledge proof. They may preserve norms, inner products, attention patterns, or other invariants. Public-weight Procrustes and norm attacks are included to demonstrate this boundary. Colluding workers, malicious computation, endpoint metadata, global timing, power/cache/TLB channels, physical bus attacks, and compromised attestation roots require separate mitigations.

PRG-based masking is not an information-theoretic one-time pad. Raw uniformly random Fortress shares can provide information-theoretic hiding only under their independence and non-collusion assumptions. The default seeded activation transport provides computational hiding instead; fresh operation, row, and role-index seed derivation does not change that classification. Constant-load MoE padding makes packet sizes uniform but does not eliminate timing, TLB, cache, power, or implementation side channels. The uniform page-touch path is a mitigation to measure, not a proven elimination.

Independent sanitizer kernels cannot prove every physical register or SRAM location is erased. Python/framework copies and host root/hypervisor access limit physical-erasure claims. dm-verity verifies stored artifacts, not runtime computation.

Finite-field Freivalds checks have their standard algebraic domain. BF16/FP16/FP8 verification uses tolerances and empirical differential checks, not the finite-field probability bound.

## Attestation trust roots

The AMD adapter invokes `snpguest verify attestation`. Intel uses the `sgx_dcap_quote_verify` API with full collateral and expiration. NVIDIA supports the local `verifier.cc_admin` path and remote NRAS verification; NRAS requires fresh nonce-bound evidence and a nonempty signed token. Composite confidential-GPU release requires both accepted CPU and GPU evidence rather than treating one device as proof of the other. These interfaces do not establish immunity to physical PCK extraction, quote replay, forged CPU/GPU binding, malicious firmware, a compromised verifier host, or a compromised remote attestation service. Deployments must pin trust roots and review current vendor guidance.

Cloud-provider evidence has distinct trust assumptions. Alibaba's relying-party client verifies the OIDC RS256 signature against the service JWKS, issuer/audience/time claims, `acstdxnvgpu`, runtime data, and requested policy reports; HTTP success alone is not accepted. OCI uses a nonce-bound Veraison challenge and a pinned ES256 verifier key, requiring affirming SEV-SNP hardware/runtime-opacity appraisal and expected measurements. AWS validates the Nitro COSE signature, pinned root-first certificate chain, PCRs 0/1/2, nonce, and session public key before attested KMS decryption. IBM uses Intel DCAP. The AF_VSOCK parent relay forwards opaque datagrams only and provides no confidentiality or enclave-attestation guarantee of its own. Provider API tests are mocks, not physical evidence. CPU-only OCI, AWS, and IBM paths do not attest a GPU, and GCP G4 remains unsupported until its separate AMD evidence path exists.

## Local evidence

CPU tests cover cache/request cleanup, sealed memfds, nonce/binding failures, finite-field and floating-point checks, Procrustes recovery, norm leakage, and real model equivalence. CUDA tests are executable and skip cleanly without CUDA. At `a42b552`, one RTX 4090 passed 20 native/hardware tests and 18 `compute-sanitizer` tests with zero reported errors; this is scoped native-path evidence, not complete physical-memory erasure or independent multi-host acceptance. Full distributed-model, TEE, side-channel, and performance claims remain hardware-validation work.


## Fortress prompt armour and canaries

`xurcroh.fortress.prompt_armour` detects explicit credentials and email addresses locally and can run a token-classification model strictly from a local checkpoint with network loading disabled. Recognized spans are replaced with random-session placeholders and restored in generated text. Recognition coverage is model-dependent and is not a guarantee that every name or secret is found. Placeholder originals are held in wipeable bytearrays, but Python strings, caller-owned inputs, generated strings, and framework copies cannot be comprehensively zeroized by this API.

Prompt armour is opt-in (`security.prompt_armour`, default off) because it changes the text the model reads and can therefore change the answer. When enabled, every text part of a chat request is armoured before tokenisation on the trusted client, streamed and non-streamed output is restored, and `execution.armoured_entities` reports how many spans were replaced so the substitution is never silent. `security.prompt_armour_model` selects the optional local recognition checkpoint.

`xurcroh.fortress.canary` mixes real and decoy call schedules and associates unique share canaries with their observer set. A trip means that a registered secret was observed by the trusted monitoring integration; it attributes the observer set and triggers revocation, but does not prove which observer disclosed it. The F0/M0 reports use a simulated external observation of an actually transmitted share, not an independent monitoring service or a public red-team result.


## Fortress role session establishment

A Fortress role session (`xurcroh.fortress.session`) is opened with one round trip in the same fixed-size frames as every other call. The client sends a fresh ephemeral public key and a secret sealed to the worker's static recipient key. The worker opens it, seals a secret of its own to the client's ephemeral key, and returns it with the digest of the artifacts it loaded and, when it holds an identity key, a signature over a hash of the whole exchange. Session keys are derived from both secrets and that hash. Both seals are HPKE (RFC 9180) with the combined ML-KEM-768/X25519 KEM, HKDF-SHA256 and ChaCha20-Poly1305 as implemented by the `cryptography` library (`xurcroh.kem`), so recovering either secret requires breaking both key exchanges.

- **Forward secrecy.** The worker's static key alone does not open a recorded session, because the worker's secret was sealed to an ephemeral key the client discards after the handshake. At every rotation both sides replace the key by a one-way derivation of the previous one. Python cannot guarantee that discarded key bytes are erased from process memory; erasure is best effort.
- **Binding to TLS.** On a direct route both ends mix a TLS exporter value for their connection into the handshake, so a handshake made on one TLS connection is refused on another. On a relayed route the client's TLS connection ends at the entry relay, so there is no shared TLS session to bind to and the session is unbound; a task trace reports which case applied.
- **Who is authenticated.** The worker is authenticated by its static recipient key and, when the client pins it, its identity signature. The client is authenticated by its mutual-TLS certificate; on a relayed route the worker authenticates the exit relay instead.
- **Expiry.** A worker no longer re-creates an expired session from a resent envelope. It refuses the packet and the client opens a new session.

`protocol/fortress_role_session.pv` models this exchange over a fully attacker-controlled channel. Three queries hold: secrecy of requests and of responses, including after the worker's static key is disclosed, and injective agreement on the session key. The model represents client authentication as a client signature standing for the mutual-TLS certificate with channel binding, so it does not cover relayed routes. A first version without client authentication failed the response-secrecy query, which is why that assumption is stated. The computational security of the KEM and HPKE, TLS itself, the replay window, the ratchet, compromise of an identity or ephemeral key, and side channels are outside the model.

## HPKE session establishment (stage and media sessions)

The older stage-worker and protected-media sessions described here are not used by Fortress role workers and remain classical.

Interactive stage and protected-media sessions use RFC 9180 HPKE (`X25519HkdfSha256` with ChaCha20-Poly1305) to seal a fresh random session master. HPKE Base mode alone does not authenticate the client; peer authentication comes from mutually authenticated QUIC/TLS. Stage HPKE associated data binds the session identifier and authentication token; media HPKE associated data binds the media session identifier. Directional AEAD keys, replay windows, and monotonic epoch rotation are derived only after that authenticated establishment. The legacy raw-X25519 session-exchange path has been removed. Offline shard recipient sealing is a separate artifact-custody mechanism, not this interactive handshake.

`protocol/fortress_session.pv` models the mutually authenticated establishment as a private channel while leaving subsequent ciphertext traffic adversary-visible. `scripts/check_proverif.py` requires every summary query to be true, so a ProVerif exit status of zero cannot hide a false secrecy or correspondence query. Hybrid post-quantum KEM details, computational HPKE proofs, replay windows, nonce exhaustion, compromise, and side channels remain outside this symbolic model.


## Cryptographic scope today

These statements bound what may be claimed. Each is taken from the code, not from intent.

- **Post-quantum.** On the Fortress path the QUIC/TLS key exchange (`X25519MLKEM768`, asserted by `crates/transport/tests/quic.rs`), the role session handshake and the onion layers all combine X25519 with ML-KEM-768. Signatures on task traces, log tree heads, the transparency log, release manifests, ladder evidence, worker registrations and worker checkpoints are Ed25519 and ML-DSA-65 together, and both must verify (`xurcroh.signatures`). TLS certificates are classical (RSA), which affects live impersonation by a quantum adversary and not the secrecy of recorded traffic. The older stage-worker and protected-media sessions and shard recipient sealing, which Fortress role workers do not use, are still X25519 only. No NIST known-answer vectors for ML-KEM or ML-DSA are checked in; the implementations are those of the `cryptography` library and aws-lc.
- **Forward secrecy.** TLS 1.3 provides it on every link. The Fortress role session adds it end to end between client and worker and binds to TLS on direct routes only (see "Fortress role session establishment"). The older stage and media sessions seal their master to a static key and are not forward-secret.
- **Secret sharing.** Shares drawn from the operating system generator are uniformly random and hide information-theoretically under non-collusion. Seed-expanded shares (`fortress_seed`, and seeded activations, which are the default) are computational. A task trace states which kind was used.
- **Result checking.** Each remote worker result is checked against two independent challenge vectors per weight share, drawn at compile time and never sent to a worker. Each bounds the chance of accepting a wrong result by 1/p, so together the bound is about 2^-64 (`FREIVALDS_ROUNDS`). The in-process native grid path still verifies one challenge. The challenges are fixed for the life of a compiled model, not drawn per request.
- **Transparency log.** `xurcroh.public_log` is an append-only Merkle log of digests (task-trace hashes, model manifest digests, release digests) with inclusion and consistency proofs, signed tree heads and witness countersignatures. The client can publish every trace hash to it and can refuse a model whose manifest digest is not in it. The project does not operate a log or a witness, the write token is a shared bearer secret, and the client does not check its own build against the log. The older `xurcroh.transparency` service for worker image measurements is still a signed hash chain without proofs or witnesses.
- **Attestation.** Verifiers exist for AMD SEV-SNP (through `snpguest`), Intel TDX (DCAP), and NVIDIA (remote service). Fortress role workers started by the managed deployment run with `--allow-unattested` outside TEE mode, and the role worker command has no attestation callback, so a TEE-mode Fortress worker refuses to start. Fortress on commodity hardware is unattested and a task trace says so.
- **Worker checkpoints.** A role worker with an identity key signs the digest of the artifacts it loaded and a running hash of its session traffic; the client fails a request whose checkpoint does not match its own view or the pinned key and digest. This identifies a key and its claimed artifacts. It is not attestation and does not show the key is held in protected hardware.
- **Placement labels.** Country and CPU vendor come from operator configuration and are not verified.
- **Formal model.** `protocol/fortress_role_session.pv` models the role session over a public channel with disclosure of the worker's static key; `protocol/fortress_session.pv` models the older session and assumes an authenticated establishment channel. Neither models the hybrid KEM computationally, the replay window, or compromise of an identity key.

## Oblivious relay and traffic analysis

`xurcroh.fortress.relay` forwards mutually authenticated QUIC calls through a chain of allowlisted onion relays. A route is configured per worker with the `onion_public` and `relay_path` labels (entry relay first, any number of hops); each relay runs as `python -m xurcroh.fortress.relay_cli` and each worker takes `--onion-key`, after which it accepts only onion-wrapped traffic. Each onion layer is sealed to one hop with X25519 and ML-KEM-768 together (`xurcroh.fortress.onion`) and reveals only that hop's authorized next address; the role session remains end-to-end between client and worker. Onion keys are created with `python -m xurcroh.kem`, and each extra hop adds two 1 KiB blocks to a frame. The entry relay observes the client's network address, the exit relay observes the worker's address, and each worker observes only the exit relay. With one relay, that relay sees both ends; separating client from worker needs at least two relays run by parties that do not collude. Relays are not provisioned by the managed SSH deployment and must be started by the operator. Only requests are layered: a response is protected by the end-to-end session and is forwarded unchanged by each hop. Relays do not batch, delay, or reorder. A global observer can still correlate timing and volume, so this is not Tor/I2P-level anonymity or proof against intersection attacks. Fixed-size frames and constant-rate verified cover calls reduce direct size/workload signals but do not remove scheduling or microarchitectural leakage. The current local leave-one-out nearest-mean timing result is recorded in `docs/evidence/fortress/transport.json` (balanced accuracy 0.572 versus a 0.5 baseline for that run), not presented as general classifier resistance.

## SSH datagram relay fallback

The optional `datagram_tunnel` deployment path forwards framed UDP datagrams through SSH local port forwarding when provider UDP is unusable. Its TCP and UDP listeners bind to loopback, each client source receives an isolated relay connection, and worker/relay PIDs are included in teardown. QUIC mutual TLS, application session authentication, and payload encryption remain end-to-end; SSH is an additional transport layer, not a replacement for either. The relay does not provide anonymity against SSH hosts, providers, global observers, or traffic analysis. Local tests demonstrate a real QUIC round trip, while the physical relay run did not complete its numerical/SDK gate and is not claimed as validated.
