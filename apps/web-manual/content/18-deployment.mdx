# 18. Deployment

<Evidence type="local">Reproducible build, configuration, and validation scripts</Evidence>

Install the Python environment with `./scripts/bootstrap-python.sh`, the pinned Rust toolchain from `rust-toolchain.toml`, and the web lockfile with `npm ci`. Do not commit provider credentials, private keys, checkpoints, encrypted shards, or sensitive logs.

## Startup sequence

1. Compile model shards and verify the manifest on a trusted build host.
2. Build the Rust extension and native allocator on the intended GPU architecture.
3. Start the blind controller and workers with pinned certificates and required strict flags.
4. Register workers with fresh Ed25519 signatures and validate capabilities.
5. Create a client circuit and run numerical, cancellation, failure, and cleanup checks before production traffic.

For Fortress models, SSH-configured hosts are provisioned automatically unless `provision_workers=false` is explicit; no separate controller endpoint is required. The SDK discovers GPUs with `nvidia-smi`, resolves pinned checkpoints, compiles recipient-sealed role artifacts, deploys a committed source archive, generates deployment-scoped mutual TLS identities, and starts authenticated QUIC role workers. Four hosts form the default two-share grid, and multiple models receive isolated role packages and ports. Credentials are key/agent based or indirectly supplied and never embedded in commands. Shutdown waits for in-flight cancellation and role exit; failed SSH teardown retains a local recovery workspace for a `close()` retry. Production workers still require strict transport and recipient isolation; development HTTP is restricted to local testing. `python -m xurcroh.stage_worker` loads one recipient-sealed stage from a manifest. The public model definition supplies `manifest_path`, the local tokenizer path, and an indirect `boundary_key_env`; strict mode rejects full-model remote checkpoints instead of treating HTTPS alone as model-custody protection.

The repository includes a locked multi-stage `Dockerfile`, loopback-only `deploy/compose.yaml`, and TLS-oriented `deploy/kubernetes.yaml`. Compose intentionally uses development HTTP on one network; it is not a zero-trust deployment. Kubernetes requires operator-supplied CA certificates, checkpoint storage, ingress policy, attestation, and strict shard configuration. Full commands and resource checks are in `docs/deployment.md`; no container or physical cluster deployment is claimed as locally verified on this host.

Remote TEE stages expose `/v1/attestation/challenge` and `/v1/attestation/evidence`. Clients bind each fresh nonce to workload, artifact, and public-key hashes, then verify AMD/Intel evidence locally. Tests exercise real stage inference and tamper rejection with explicit hardware-verifier doubles; physical TEE success is unverified. NVIDIA remote-report transport remains unsupported and fails explicitly.

Use `scripts/gpu/validate.sh` for native and CPU checks. EROFS/dm-verity and AMD/Intel/NVIDIA attestation are optional defense-in-depth, not blanket deployment requirements. `docs/gpu-agent-handoff.md` provides the funded-agent execution procedure, and `scripts/fortress/validate_handoff.py` validates all 21 offline ladder commands without contacting a provider. Multi-model manifests require `--model`; unresolved revisions and final zero artifact fingerprints are stop conditions. The [hardware plan](/22-experimental-reports) lists Stage Two acceptance tests.
