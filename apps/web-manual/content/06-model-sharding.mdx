The offline compiler reads `config.json` plus `model.safetensors` or its index, detects layer structure, partitions contiguous stages, applies verified dense/MoE transformations, and separates the client embedding/LM-head boundary. It rejects unsupported layouts instead of silently copying them.

## Versioned artifacts

A `.xurcroh` file contains an 8-byte magic, format version, bounded canonical JSON header, 96-bit nonce, and ChaCha20-Poly1305 ciphertext. Header and prefix are authenticated associated data. Decryption additionally checks the plaintext digest. Per-stage DEKs are wrapped independently and never stored in the manifest as plaintext.

<Equation tex="C=\operatorname{AEAD}_{K_s}(N_s, S_s, AAD_s),\quad AAD_s=\operatorname{header}_s" />

`SecureShardLoader` requires the correct key and stage metadata, decrypts into page-locked mutable RAM, loads safetensors from bytes, then wipes/unlocks the buffer and zeroes CPU tensors. Wrong keys, modified ciphertext, truncation, missing files, and unexpected stages fail closed. `verify_manifest` validates artifact hashes, common checkpoint identity, and complete layer coverage.

`VerityPackager` provides real EROFS/dm-verity command automation. It does not imply runtime integrity; that requires separate workload checks and hardware validation. See the [developer reference](/19-developer-reference) and [thin-client boundary](/19-developer-reference#client-boundary).

## Fortress role packages

Fortress uses a separate role-artifact format for the additive share grid. A seeded compilation uses HKDF-SHA256 domains for the operation, share index, basis purpose, and epoch. The `xurcroh-fortress-role-v2` artifact contains a non-final share's seed and matrix shape; the worker expands its own matrix with ChaCha20. The final share remains a full `xurcroh-fortress-role-v1` AONT-RS artifact because it depends on the quantized weight and every preceding share. Seed-expanded shares provide computational obfuscation, not information-theoretic security.

During deployment, the compiler writes each operation's role artifacts immediately and then discards worker matrices and dispersal bundles. The current remote client still retains quantized `int8` weight matrices, client-only signed permutations, and Freivalds challenge vectors; removing those matrices from production clients is an active scalability requirement, not a completed thin-client claim. Integrity challenges are fresh OS-generated secrets rather than values derived from the deployment seed. Arithmetic and reconstruction use canonical elements of the field \(2^{32}-5\), with compact 32-bit transport words. The official-model remote path uses FP32 client-side nonlinear computation; FP64 remains available for reference verification. Artifact distribution uses authenticated SSH, and inference uses mutually authenticated QUIC; these transport protections are distinct from the share-secrecy assumption.
